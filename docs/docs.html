FlashBot documentation

Installation, configuration, and reference for version 0.3.0.

Introduction

FlashBot is a command-line tool that automates the firmware workflow for microcontroller boards. When a board is connected, FlashBot identifies it, finds the firmware in your workspace that targets it, builds that firmware with arduino-cli or PlatformIO, uploads it, verifies the result over the serial port, and records the outcome in a local database.

StageBehaviour
DetectListens for USB hotplug events (udev on Linux, polling elsewhere) and reads the USB vendor and product IDs.
IdentifyMaps the USB ID to a board name, FQBN, and PlatformIO board ID. Unrecognised boards can be registered once.
SelectFinds every Arduino sketch and PlatformIO environment that targets the board.
BuildCompiles the selection. Arduino builds are skipped when the sources have not changed since the last successful build.
FlashUploads to the board, retrying where the platform benefits from it.
TestWaits for the board to re-enumerate and runs the serial tests declared for the sketch.
RecordStores the run, the failing stage if any, and the test outcome.

Requirements

  • Python 3.10 or later.
  • Linux. This is the primary platform and uses udev for hotplug detection. Other platforms fall back to polling and are untested.
  • arduino-cli for Arduino sketches.
  • PlatformIO Core for PlatformIO projects. Optional.
  • Membership in the dialout group for serial port access.

Installation

  1. Clone the repository 
    git clone https://github.com/Harsha685/Flash_Bot.git
cd Flash_Bot
  2. Install the package

    With Poetry, for development:

    poetry install
poetry run flashbot --version

    Or with pip, which installs the flashbot command into the active environment:

    pip install .
  3. Install arduino-cli cores

    Install the cores for the boards you use. The ESP32 and RP2040 cores need their package indexes registered first.

    arduino-cli config add board_manager.additional_urls \
  https://espressif.github.io/arduino-esp32/package_esp32_index.json \
  https://github.com/earlephilhower/arduino-pico/releases/download/global/package_rp2040_index.json
arduino-cli core update-index
arduino-cli core install arduino:avr arduino:renesas_uno esp32:esp32 rp2040:rp2040
  4. Grant serial port access 
    sudo usermod -aG dialout $USER   # log out and back in afterwards
  5. Verify the environment 
    flashbot doctor

    doctor checks Python, arduino-cli and its installed cores, PlatformIO, serial permissions, hotplug support, ModemManager, and the workspace.

The repository includes example sketches, so it can be used as a workspace directly. From the repository root:

flashbot

Connect a board. FlashBot shows the identified board, lists matching firmware, and runs the pipeline for the entry you select:

flashbot flash serial_test

Workspace layout

FlashBot reads firmware from, and writes its state to, a workspace directory:

<workspace>/
├── sketches/    Arduino sketches and PlatformIO projects
├── config/      user_boards.json, firmware_manifest.json (generated)
├── build/       compiler output, one directory per board and sketch
└── logs/        flashbot.db

The workspace is resolved in this order:

  1. The --workspace option.
  2. The FLASHBOT_HOME environment variable.
  3. The current directory, if it contains a sketches/ directory.
  4. ~/.flashbot.

Create a workspace with flashbot init <path>. The active workspace is shown in the banner when FlashBot starts.

Live updates

While flashbot run is active, new or removed sketches and projects are picked up automatically. No restart is required.

Arduino sketches

The folder path of an Arduino sketch encodes the board's fully qualified board name (FQBN):

sketches/<vendor>/<arch>/<board>[/<option>=<value>...]/<name>/<name>.ino
FQBNSketch location
arduino:avr:unosketches/arduino/avr/uno/blink/blink.ino
arduino:avr:nano:cpu=atmega328oldsketches/arduino/avr/nano/cpu=atmega328old/imu/imu.ino
esp32:esp32:esp32s3sketches/esp32/esp32/esp32s3/web_server/web_server.ino
rp2040:rp2040:rpipicosketches/rp2040/rp2040/rpipico/blink/blink.ino
  • The .ino file name must match its folder name.
  • Board options become additional folder levels, one per option, in the form key=value.
  • Additional .cpp, .c, and .h files in the sketch folder are compiled and included in change detection.

Run flashbot sketches to list everything that was discovered. Folders that do not follow the layout are reported as warnings with the reason.

Build cache

Each sketch and FQBN pair has its own build directory under build/. Before compiling, FlashBot hashes every source file in the sketch folder. If the hash matches the last successful build and the build output is present, compilation is skipped and the existing binary is uploaded. Use --no-cache to force a rebuild.

PlatformIO projects

Any directory under sketches/ that contains a platformio.ini is treated as a PlatformIO project. Each [env:...] section becomes a separate target and is offered for boards whose PlatformIO board ID matches the environment's board value. Values from the shared [env] section and from extends are applied. 

sketches/platformio/heartbeat/
├── platformio.ini
├── flashbot.json
└── src/main.cpp
[env]
framework = arduino
monitor_speed = 115200

[env:esp32dev]
platform = espressif32
board = esp32dev

[env:uno_r4_wifi]
platform = renesas-ra
board = uno_r4_wifi

Library dependencies are declared with lib_deps in platformio.ini, as usual for PlatformIO.

FlashBot runs pio run to build and pio run --target upload --upload-port <port> to flash. PlatformIO performs its own incremental builds.

Matching environments to boards

Built-in boards carry their PlatformIO board ID (for example esp32dev or uno_r4_wifi). For other boards, use one of the following:

  • Register the board with a PlatformIO ID: flashbot boards add VID:PID --fqbn ... --pio-board my_board.
  • Pin the environment to an FQBN in platformio.ini:
[env:custom]
board = my_custom_board
custom_flashbot_fqbn = esp32:esp32:esp32s3

To flash or build a specific environment, pass --env:

flashbot flash heartbeat --env esp32dev
flashbot build sketches/platformio/heartbeat --env uno_r4_wifi

Libraries

A flashbot.json file next to an Arduino sketch holds per-sketch settings. Its libraries key lists the Arduino libraries the sketch needs, so it builds on any machine, including CI runners: 

{
  "libraries": ["Adafruit BMP280 Library", "Servo@1.2.1"]
}

Before compiling, FlashBot installs the listed libraries with arduino-cli lib install. Use the names shown by arduino-cli lib search, and append @version to pin a release. Libraries that are already installed are left as they are. When compilation is skipped because the sources are unchanged, no installation is attempted.

Post-flash tests

After uploading, FlashBot waits for the board to re-enumerate, following it to a new port if the path changes, then opens the serial port and runs the test suite. Without a test file, the suite checks that the port opens, which confirms the new firmware booted.

To define tests, add them to the flashbot.json file next to the sketch, or in the root of a PlatformIO project:

{
  "baud": 9600,
  "boot_delay": 2.0,
  "tests": [
    {"name": "boot_banner", "expect": "READY", "timeout": 5},
    {"name": "ping", "send": "PING", "expect": "PONG"},
    {"name": "status", "send": "STATUS", "expect": "^OK", "regex": true}
  ]
}
FieldDefaultDescription
bauddetectedPlatformIO monitor_speed, then the first Serial.begin() in the source, then 9600.
boot_delay2.0Seconds to wait after opening the port. Opening the port resets most Arduino-compatible boards.
tests[].nametest_NName shown in results and in the history report.
tests[].sendnoneLine to send. Omit to only wait for output, for example a boot banner.
tests[].expectany replyText a received line must contain.
tests[].regexfalseTreat expect as a regular expression.
tests[].timeout2.0Seconds to wait for a matching line.

The firmware side only needs to read lines and print replies:

void setup() {
  Serial.begin(9600);
}

void loop() {
  if (Serial.available()) {
    String cmd = Serial.readStringUntil('\n');
    cmd.trim();
    if (cmd == "PING") Serial.println("PONG");
  }
}

A run is recorded as successful only if the build, the upload, and every test pass. Use --no-test to skip testing.

Waiting for boot output

Tests without send see what the board prints after FlashBot opens the port. Boards that reset when the port opens (Uno, Nano, Mega, and ESP32 boards with a CP210x or CH340 bridge) print their boot output again at that point. Boards with native USB (Uno R4, Leonardo, Pico, ESP32-C3/S3) do not, so a message printed only once at boot can be missed. For those boards, test periodic output or use a send and expect pair.

Board registration

When an unrecognised board is connected in interactive mode, FlashBot shows its USB ID and offers a list of common boards grouped by vendor, with an option to enter any FQBN. The registration is saved to config/user_boards.json and used from then on. 

{
  "1a86:7523": {
    "name": "Nano clone",
    "fqbn": "arduino:avr:nano:cpu=atmega328old"
  }
}

Registrations can also be managed from the command line:

flashbot boards list                    # built-in and user boards
flashbot boards add                     # register the connected unrecognised board
flashbot boards add 16c0:0483 --name "Teensy 4.1" --fqbn teensy:avr:teensy41
flashbot boards remove 16c0:0483
Generic USB-serial bridges

CP210x, CH340, and FTDI bridges are used by many different boards. If one is mapped to the wrong board, register the correct board for that USB ID; user registrations take precedence over the built-in table.

Serial monitor and plotter

After a successful interactive run, FlashBot offers to open either tool on the board's current port with the detected baud rate. Both are also available directly:

flashbot monitor                        # auto-detect port, choose baud rate
flashbot monitor /dev/ttyUSB0 -b 115200 -l logs/session.log
flashbot plotter --labels temperature humidity

The monitor prints timestamped output and sends each line you type. The plotter accepts labelled values such as temp: 24.5, hum=60, or bare numbers separated by commas, tabs, or spaces, and shows a trend, the latest value, and the range for each series.

Unattended operation

flashbot run --auto never prompts. For each recognised board it flashes the most recently modified matching firmware, or the one named with --sketch, runs the tests, records the result, and waits for the next board. Unrecognised boards are logged and skipped. 

flashbot run --auto --sketch serial_test

Parallel flashing

With --jobs N, up to N boards are handled at the same time, which suits teaching labs and production stations with a USB hub:

flashbot run --auto --jobs 4 --sketch serial_test
  • Each output line is prefixed with the board's port, for example [ttyUSB0].
  • Boards that share a build directory (the same sketch for the same FQBN) compile and upload one at a time; their tests still run in parallel.
  • Identical boards without a USB serial number, such as two CH340 clones, are told apart by their port.

systemd service

The repository includes a template unit, flashbot.service. Set the user and paths, then install it:

sudo cp flashbot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now flashbot
journalctl -u flashbot -f

Docker

The image contains arduino-cli with the AVR, Renesas, ESP32, and RP2040 cores, and PlatformIO Core. It runs in unattended mode by default.

docker compose up --build

The container runs privileged with /dev and /run/udev mounted so it receives hotplug events. The sketches/, config/, logs/, and build/ directories are mounted from the host, and PlatformIO packages are cached in a named volume.

Continuous integration

flashbot build compiles firmware without hardware and exits with a non-zero status if any build fails, so it can gate pull requests.

flashbot build                          # every target in the workspace
flashbot build --fqbn esp32:esp32:esp32 # only targets for one board
flashbot build serial_test              # by name
flashbot build path/to/sketch --fqbn arduino:avr:uno

A sketch outside sketches/ has no FQBN in its path, so --fqbn is required.

Machine-readable results

flashbot build and flashbot flash can write their results for CI dashboards:

flashbot build --junit reports/build.xml
flashbot flash serial_test --yes --json reports/flash.json --junit reports/flash.xml

The JUnit XML file contains one test suite per target and one test case per step: build, upload, and each post-flash test, with the toolchain's error message on failures. The JSON file contains a summary and the same per-step detail.

GitHub Actions

The repository's workflow, .github/workflows/ci.yml, runs the unit tests on Python 3.10 to 3.13, installs arduino-cli and PlatformIO, compiles the Uno R4 and Nano firmware, and uploads the JUnit reports as build artifacts. It can be copied into a firmware repository and adjusted to the cores it needs.

Architecture

USB hotplug ──> detector ──> cli (Session) ──> pipeline ──> flasher ──> tester ──> logger
                   │                │                          │
              boards registry   firmware scanner         arduino-cli / pio
ModuleResponsibility
detector/Built-in USB IDs and the user registry, port enumeration, identification, re-enumeration tracking, and the udev listener with a polling fallback.
firmware/Discovery of Arduino sketches and PlatformIO environments, platformio.ini and flashbot.json parsing, the manifest, and live rescans.
flasher/The get_flasher factory, a generic arduino-cli flasher with build caching, an ESP32 variant with upload retry, and the PlatformIO flasher.
pipeline/The state machine that runs build, flash, and test, and records the result.
tester/flashbot.json loading, baud detection, line-oriented serial I/O, and test execution.
logger/SQLite storage with automatic migrations, the history report, and JSON and JUnit XML export.
tools/Serial monitor and serial plotter.
cli.py, ui.pyCommand implementations, Rich panels, and prompts.

Design notes

  • Hotplug events are handled on the main thread. The listener thread only queues events, so prompts and Ctrl+C behave normally, and events from a board resetting after upload are discarded by a short cooldown.
  • The flasher factory chooses the toolchain. Supporting a new build tool means one BaseFlasher subclass and one branch in get_flasher; the pipeline does not change.
  • Build caching is per sketch and per FQBN. A cached binary always belongs to the sketch being flashed.
  • The state machine is hardware-independent. The flasher, port waiter, and test runner are injected, which lets the unit tests cover every outcome without a board.

Troubleshooting

Start with flashbot doctor, flashbot devices, and flashbot sketches. Together they show the toolchain state, how the board was identified, and what firmware was found.

No firmware found for a board

The folder path does not produce the board's FQBN, or no PlatformIO environment uses its board ID. Compare the FQBN in flashbot devices with the paths in flashbot sketches, and check for layout warnings.

Permission denied on the serial port

Add your user to the dialout group with sudo usermod -aG dialout $USER, then log out and back in.

Device or resource busy

Another program holds the port. Close other serial monitors. On Ubuntu, ModemManager often claims new serial devices; disable it with sudo systemctl disable --now ModemManager.

Platform not installed

Install the core named in the error, for example arduino-cli core install esp32:esp32. flashbot doctor lists installed cores.

ESP32 upload cannot connect

FlashBot retries ESP32 uploads once. If the board still does not enter the bootloader, hold BOOT while the upload starts. Boards without auto-reset circuitry may need a 10 uF capacitor between EN and GND.

Board did not reappear after upload

The firmware may need longer to start, or the board enumerated with a different USB ID, for example a Raspberry Pi Pico running MicroPython. Increase boot_delay in flashbot.json, or check the new ID with flashbot devices.

Wrong board detected

The board uses a USB-serial bridge that is shared with other boards. Register the correct board for that USB ID with flashbot boards add VID:PID.
